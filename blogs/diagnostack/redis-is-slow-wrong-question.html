Why "Redis Is Slow" Is the Wrong Question

A dashboard can tell you that something is wrong. It can't tell you what broke, why it broke, or when the trouble actually started. Those three gaps are where production incidents live.

Duong Hoai Thuong  ·  9 min read

02 FIX the specific change that resolves it
03 WHEN it started, down to the command
Three questions a monitoring graph was never built to answer.

Somewhere between 2 and 3 a.m., latency on the checkout service starts creeping up. By the time someone is paged, p99 has tripled. The Redis dashboard is open in one tab — CPU is fine, memory is under 60%, connected clients look normal. Every graph is green. And yet the thing the graphs were supposed to explain is still happening.

This is the moment where "Redis is slow" stops being useful as a sentence. It's a symptom, not a diagnosis. The engineer staring at that dashboard doesn't need another metric to confirm that something is off — they already know that. What they need is an answer to three much narrower questions: what specifically is failing, how do I fix that specific thing, and when did it start.

Monitoring answers a different question than the one you're asking

Most Redis setups lean on Prometheus and Grafana, or a general-purpose APM tool bolted onto Redis as an afterthought. These tools are good at one job: showing you that a metric crossed a line. Memory climbed. Ops per second dropped. Connected clients spiked. That's monitoring, and it's necessary — but it stops exactly where the real work begins.

Observability is supposed to pick up from there, and it does, in theory. In practice, most Redis observability is still just monitoring with more dashboards. More panels, more colors, more thresholds to tune — but still no path from "the graph moved" to "here is the command, the client, and the timestamp responsible for it."

Two incidents that look identical on a graph

Consider two on-call scenarios that produce the exact same symptom — a latency spike on a Redis-backed endpoint — but require completely different fixes.

Scenario A. A developer ships a new admin feature that calls KEYS user:* to build a debug report. On a keyspace with a few hundred thousand keys, that single command blocks the Redis event loop long enough to stall every other client waiting behind it. CPU barely moves. Memory doesn't budge. The only trace is a single entry in SLOWLOG with an execution time that shouldn't exist in a properly indexed access pattern.

Scenario B. Traffic grows past what maxmemory allows, and Redis starts evicting keys under an LRU policy to stay under budget. The eviction itself is fast, but the application wasn't built to tolerate a jump in cache misses, so every one of those evictions turns into an extra round trip to Postgres. The dashboard shows the same shape of latency spike as Scenario A — but the fix is memory sizing and eviction policy, not a code review of a debug endpoint.

A metrics dashboard renders both of these identically: a line going up. Nothing about "used_memory: 58%" or "ops/sec: normal" tells you which of the two you're looking at. The only artifact that distinguishes them is the raw command trail — slowlog for the first, an eviction counter delta for the second — correlated against the exact window where latency broke.

Slowlog is the primitive most teams under-use

Redis's own SLOWLOG command is quietly one of the most useful debugging tools available, and it's almost never front-and-center in a monitoring setup. Every entry carries a timestamp, an execution time in microseconds, the offending command and its arguments, and the client that issued it. That's not a metric — it's a receipt.

The reason slowlog gets ignored isn't that it's hard to query. It's that most tooling treats it as a side table you check manually after a graph already told you to be suspicious, rather than as the first-class signal it should be. Flip that order — start from the command trail, not the aggregate metric — and "Redis is slow" stops being a mystery and starts being a lookup.

What "when" actually means

The third question is the one teams answer worst. "When did this start" usually gets approximated as "whenever the graph crossed the alert threshold," which is almost always later than the real onset. A gradual memory leak, a slow accumulation of blocked clients, a replication lag that's been quietly widening for twenty minutes — these don't announce themselves at a clean timestamp. They cross a threshold well after the underlying cause began.

Getting "when" right means correlating the metric anomaly with the exact command or event that triggered the shift — not the moment an alert fired, but the moment in the slowlog or the eviction counter where the trajectory actually changed. That's a timeline problem, not a threshold problem, and most alerting systems aren't built to answer it.

Redis-first, not Redis-as-a-checkbox

None of this is a criticism of Prometheus, Grafana, or the general-purpose APM tools that dominate this space — they're built to cover every system a company runs, and Redis is one line item among many. That breadth is exactly why Redis rarely gets more than a plugin's worth of attention: a handful of generic charts, no real grasp of what a slowlog entry means, no distinction between a keyspace-scan problem and an eviction problem.

That gap is what I'm building Diagnostack to close — a Redis-first diagnostic tool with one job: when Redis is slow, tell you what broke, how to fix it, and when it started, without fifteen minutes of manual slowlog archaeology first. It's in active build-in-public development right now, starting with the failure patterns above — full keyspace scans, eviction storms, blocking RDB snapshots — as the first diagnostic rules.
